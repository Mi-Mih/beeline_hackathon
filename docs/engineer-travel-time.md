# Как рассчитывается время передвижения инженера до точки

Статус: описание действующего пути `ROUTING_MATRIX_MODE=gateway` на 24 сентября
2026 года. Источники истины — код приложения и конфигурация, ссылки приведены
ниже. Разделы технического разбора содержат предложения, а не действующие
правила.

## Что именно считается

Для каждой поездки между двумя точками планировщик использует целое число
минут `travel.legs[].minutes`. Это время **одного направленного переезда** от
текущей точки инженера к следующей заявке. Для первой заявки текущая точка —
`technician.start_location_id`, время выезда — `technician.available_from`.
После выполнения заявки следующая поездка начинается от её точки и от момента
окончания работ. Обратный путь после последней заявки в этой модели не
прибавляется.

Дорога, ожидание начала временного окна и выполнение работ — разные величины.
`request.duration_minutes` содержит время работ и оформления документов; типовые
20 минут дороги из норматива к полученному из матрицы времени не добавляются.

## Путь числа от OSRM до плана

1. При запросе `POST /api/plan` веб-сервер проверяет
   `ROUTING_MATRIX_MODE`. В режиме `gateway` он строит новую матрицу через
   Routing Gateway и **заменяет** поле `travel`, пришедшее во входном JSON.
   Это происходит до разбора заявки планировщиком
   ([`backend/web.py`](../backend/web.py)). В Compose выставлено
   `ROUTING_MATRIX_MODE=gateway` ([`deploy/routing/compose.yml`](../deploy/routing/compose.yml)).
2. Берутся все `locations` с `id`, `longitude`, `latitude`. Координаты должны
   присутствовать и попадать в допустимые диапазоны; геокодирования адреса на
   этом шаге нет. Список видов транспорта берётся из `technicians[].vehicle`.
   Для каждого вида транспорта Gateway запрашивается отдельно
   ([`points_from_payload`, `modes_from_payload`, `travel_from_gateway`](../backend/routing_gateway.py)).
3. Gateway выбирает соответствующий OSRM-инстанс: `OSRM_CAR_URL` для `car`,
   `OSRM_FOOT_URL` для `pedestrian`, если он настроен. OSRM Table получает все
   координаты в порядке списка и возвращает **матрицы времени в секундах и
   расстояния в метрах**. Запрос содержит `annotations=duration,distance`.
   Одна строка матрицы означает точку отправления, столбец — точку назначения.
   OSRM выбирает маршрут по весам собранного графа; возвращаемое расстояние
   относится к этому маршруту, а не обязательно к кратчайшему по километрам
   ([`OsrmTableClient.matrix`](../backend/routing_gateway.py),
   [OSRM Table API](https://github.com/Project-OSRM/osrm-backend/blob/master/docs/http.md#table-service)).
4. Gateway требует ответ `code: Ok` и полные квадратные матрицы нужного
   размера. `null`, отрицательные, бесконечные и нечисловые значения вызывают
   ошибку. Если превышен настроенный предел числа координат или OSRM
   недоступен, план не строится. Прямолинейного запасного расчёта для
   планирования нет ([`OsrmTableClient`](../backend/routing_gateway.py)).
5. Для каждой пары **разных ID** приложение создаёт отдельную дугу `from → to`
   с видом транспорта. Формула в коде такова:

   ```text
   если distance_meters == 0:
       minutes = 0
   иначе:
       minutes = max(1, ceil(duration_seconds / 60))
   distance_km = round(distance_meters / 1000, 3)
   ```

   То есть 60 секунд дают 1 минуту, 61 секунда — 2 минуты. Округление
   выполняется **для каждой дуги**, до суммирования пути. Для разных ID с
   нулевой дистанцией код также ставит ноль минут, даже если OSRM вернул
   положительное время. Дуги `A → B` и `B → A` сохраняются раздельно;
   `travel.symmetric` устанавливается в `false`
   ([`travel_from_gateway`](../backend/routing_gateway.py)).
6. Контракт проверяет, что `minutes` — неотрицательное целое число, и
   превращает дуги в `TravelTable`. Для одинаковых ID таблица возвращает
   `(0 минут, 0 км)`. При поиске она сначала берёт дугу, совпадающую с видом
   транспорта инженера. В общей модели есть поиск дуги без `mode` и, если
   `symmetric=true`, обратной дуги. Матрица, созданная Gateway, содержит
   отдельные дуги для запрошенных видов транспорта и `symmetric=false`, так
   что эти запасные варианты обычно не задействованы
   ([`contract.py`](../backend/math_core/contract.py),
   [`models.py`](../backend/math_core/models.py)).
7. По умолчанию симуляция берёт готовое `leg.minutes`. Режим включается
   полем `use_travel_history: true` у `POST /api/plan`. В интерфейсе это кнопка
   **«С калибровкой»** в окне «Калибровка времени»; нажатие только запоминает
   режим и не запускает расчёт. При включённом режиме backend находит
   медианный персональный коэффициент `actual_seconds / osrm_seconds` по
   валидным наблюдениям инженера и считает
   `effective_minutes = ceil(leg.minutes × factor)`. Нулевая дуга остаётся
   нулевой. Если наблюдений инженера нет, коэффициент равен 1.
   Кнопка **«Без калибровки»** оставляет коэффициент 1.
   Подробности формы: [travel-observation-import.md](travel-observation-import.md).
8. Для очередной заявки симуляция считает:

   ```text
   arrival_at       = departure_at + effective_minutes
   service_start_at = max(arrival_at, request.window.start)
   wait_minutes     = service_start_at - arrival_at
   service_end_at   = service_start_at + request.duration_minutes
   ```

   Если начало работ позже конца окна заявки либо конец работ позже конца
   смены, такая последовательность невыполнима. Затем `departure_at`
   следующего переезда становится равным `service_end_at`. Минуты дороги
   суммируются по дугам и попадают в `stop.travel_minutes`,
   `route.metrics.travel_minutes` и общие метрики плана
   ([`simulate_route`](../backend/math_core/simulate.py)). Алгоритм Routing
   использует те же скорректированные минуты при поиске и повторно симулирует готовый маршрут
   для выдачи остановок ([`routing.py`](../backend/math_core/routing.py)).

### Числовой пример

Инженер доступен в 09:00. OSRM вернул для пути от его текущей точки к заявке
`duration = 541` секунду и ненулевую дистанцию. Дуга получает
`ceil(541 / 60) = 10` минут; прибытие — 09:10. Если окно начинается в 09:30,
инженер ждёт 20 минут. При `duration_minutes = 70` работы заканчиваются в
10:40, и именно с 10:40 считается переезд к следующей заявке. Время дороги
остаётся 10 минутами, ожидание — 20, работы — 70.

## Что входит в число OSRM и что не добавляет приложение

OSRM рассчитывает время по дорожному графу и его профилю. Профиль может
задавать скорости участков, ограничения движения и задержки на манёврах;
стандартный автомобильный профиль обрабатывает повороты и размеченные
препятствия. Поэтому приложение **не добавляет** собственные штрафы за
повороты, светофоры, километры или время суток к `duration_seconds`
([документация профилей OSRM](https://github.com/Project-OSRM/osrm-backend/blob/master/docs/profiles.md),
[автомобильный профиль OSRM](https://github.com/Project-OSRM/osrm-backend/blob/master/profiles/car.lua)).
Реальный эффект зависит от версии профиля и полноты OSM-данных.

Сборщик этого проекта запускает `osrm-extract` со штатными `car.lua` и,
опционально, `foot.lua`, затем `osrm-partition` и `osrm-customize` без файлов
скоростей трафика ([`scripts/build_moscow_osrm.py`](../scripts/build_moscow_osrm.py)).
Поэтому результат не отражает текущие пробки и в нынешнем виде не зависит от
планируемого часа выезда. OSRM позволяет передать файлы скоростей при
`osrm-customize`, но этот механизм здесь пока не подключён
([инструменты OSRM](https://github.com/Project-OSRM/osrm-backend/blob/master/docs/tools.md#osrm-customize)).

Отдельный [`backend/travel_matrix.py`](../backend/travel_matrix.py) умеет
оценивать альтернативные маршруты с коэффициентами по времени суток и штрафами
за повороты. Это экспериментальный сборщик; путь `gateway` его не вызывает.
Также `GET /api/route` строит геометрию для карты через OSRM Route. Его
округлённое до десятых минут поле `duration_minutes` не подставляется в план
([`routing_gateway.py`](../backend/routing_gateway.py),
[`web.py`](../backend/web.py)).

По умолчанию `ROUTING_MATRIX_MODE=gateway`, поэтому `/api/plan` получает время
из OSRM. Режим `input` можно включить явно для чтения `travel.legs` из входного
JSON. Опция `use_travel_history` применяется после получения матрицы, поэтому
работает и с входными дугами, и с gateway.

## Технический разбор 1

### Что оставить

1. **Направленные дуги по отдельным видам транспорта.** Односторонние улицы и
   разные дорожные сети делают путь `A → B` отличным от `B → A`. Одно
   значение на пару или пересчёт пешего маршрута из автомобильного времени
   исказили бы доступность заявок.
2. **Один снимок матрицы на расчёт плана.** Планировщик многократно сравнивает
   варианты маршрутов. Фиксированные времена делают сравнение согласованным и
   позволяют повторить расчёт на том же входе. При каждом новом запросе плана
   в режиме `gateway` матрица запрашивается заново.
3. **Раздельный учёт дороги, ожидания и работ.** Так видно, из-за чего не
   укладывается конкретная заявка; 20 нормативных минут дороги не попадают в
   расчёт второй раз.
4. **Отказ от планирования при неполной матрице.** Скрытая замена дороги
   расстоянием по прямой или временем другого транспорта могла бы дать
   формально выполнимый, но фактически неверный маршрут. Ошибка с указанием
   отсутствующего маршрута полезнее такого плана.

### Что улучшить и в каком порядке

1. **Сначала измерить ошибку прогноза.** Сохранять для выполненных переездов
   прогноз OSRM, фактические время выезда и прибытия, вид транспорта, район,
   длину маршрута и время суток. Сравнивать медианную ошибку и долю опозданий
   по этим группам. Пока таких данных нет, нельзя обоснованно выбрать ни
   коэффициент «на пробки», ни запас минут; один общий множитель смешает
   короткие и длинные поездки.
2. **Проверять привязку координат к дорогам.** Gateway уже получает
   `snap_distances_meters` от OSRM, но построитель матрицы их не использует.
   Большое расстояние привязки может означать ошибочный адрес, точку по другую
   сторону реки или неверный профиль. Стоит выводить его в диагностику плана
   и проверять порог на реальных адресах, прежде чем блокировать план.
3. **Если данные покажут систематическую зависимость от часа, применять
   исторические скорости по периодам дня.** Для ночного плана нужны ожидаемые
   скорости завтрашнего утра и дня, а не случайное состояние пробок в момент
   расчёта. Их разумнее вводить в версионированные веса дорожного графа, чтобы
   OSRM мог выбрать другой маршрут, когда привычный маршрут замедляется.
   Простое умножение уже выбранной дуги меняет время, но не маршрут. Здесь
   потребуется продумать, какую матрицу использовать для каждого фактического
   времени отправления; нынешняя одна статическая матрица этого не умеет.
4. **При требованиях к пунктуальности ввести отдельный резерв.** Его следует
   оценивать из распределения фактической ошибки и применять при проверке
   временных окон. В ответе полезно показывать базовое время OSRM и резерв
   отдельно: тогда пользователь понимает, что 12 минут дороги плюс 5 минут
   запаса — это не 17 минут, измеренных маршрутизатором. Величину резерва
   нельзя назначить уверенно до накопления наблюдений.
5. **Не добавлять сейчас штрафы за каждый поворот и светофор.** Такие задержки
   уже могут входить в профиль OSRM; поверх них легко получить двойной счёт.
   Если измерения покажут устойчивую ошибку именно на маршрутах с большим
   числом перекрёстков, следует калибровать профиль и проверить полноту
   разметки OSM, затем сравнить точность до и после на отложенных поездках.
6. **Проверить пограничный случай нулевой дистанции.** Для разных ID код
   записывает ноль минут всякий раз, когда OSRM вернул `distance=0`, даже при
   положительной `duration`. Это может быть правильно для совпадающих точек,
   но при разных объектах требует анализа: сопоставить точки после привязки к
   дороге и решить, использовать ли ненулевое время OSRM. Не следует менять
   правило без реальных примеров и регрессионного теста.

Предлагаемый порядок: наблюдения и качество координат → проверка ошибок по
группам → калибровка скоростей или резерв там, где это подтверждено данными.
Так можно улучшить пунктуальность без произвольного увеличения каждой поездки.

## Технический разбор 2

Раздел описывает действующий путь `gateway` и не меняет его. Проверено по коду
на 24 сентября 2026 года: подмена `travel` в `POST /api/plan`, формула
`0 если метры равны 0, иначе max(1, ceil(секунды / 60))`, `symmetric=false`,
симуляция прибытия и окна, сборка графа без файлов скоростей и то, что
`travel_matrix.py` и `GET /api/route` в план не входят.

### Оценка документа

Текст пригоден как спецификация текущего расчёта. Он проводит одно число от
OSRM Table до `stop.travel_minutes`, отделяет дорогу от ожидания и работ и
прямо говорит, чего в минутах нет: пробок, норматива в 20 минут, обратного
пути, геокодирования. Числовой пример с 541 секундой сходится с формулой.
Граница между описанием и предложениями выдержана.

Два места легко прочитать шире, чем написано в коде.

1. Правило нуля минут смотрит на сырые `distance_meters == 0`. Поле
   `distance_km` округляется отдельно до трёх знаков. Участок в 0,4 м получит
   `distance_km = 0.000` и при этом не меньше одной минуты. Ноль километров в
   дуге и ноль минут — разные условия.
2. Фраза про задержки профиля означает, что профиль влияет на выбор маршрута и
   может добавить время на манёвр. Возвращаемая `duration` — это длительность
   рёбер выбранного пути. Штраф, попавший только в вес маршрута, в минуты плана
   не входит. Поэтому отсутствие собственных штрафов за поворот правильно, но
   из документа не следует, что светофор уже сидит внутри каждой дуги.

### Что в модели существенно

Планировщик оптимизирует уже округлённые минуты, а не секунды OSRM. Для
ненулевой дистанции каждая дуга получает потолок и не меньше одной минуты,
округление делается до суммирования. Сумма потолков не меньше потолка суммы:
день из коротких переездов накапливает до одной лишней минуты на дугу и
систематически удорожает маршрут из многих коротких плеч относительно
меньшего числа длинных. При разборе ошибки прогноза сырые секунды OSRM и
минуты, которые увидел поиск, нужно хранить отдельно. Иначе потолок смешается
с ошибкой графа.

Один статический снимок на весь план — главное ограничение точности, больше
чем отсутствие отдельного штрафа за перекрёсток. По этому снимку выбирается
маршрут, а не только проверяется окно. Запас минут, добавленный к уже
выбранной дуге, не вернёт путь, который свободный граф предпочёл загруженному.
Смещение «утром медленнее, чем в матрице» лечится скоростями в весах графа.
Разброс вокруг уже верного среднего лечится резервом при проверке окна. Это
разные поправки; резерв, поставленный раньше калибровки, прячет смещение
внутри большего числа.

Отсутствие обратной дороги после последней заявки — граница задачи, а не
недочёт OSRM. Смена считается выполненной, когда закончены работы на последней
точке. Если позже понадобится возврат к заданному месту к `shift_end`, это
новая дуга от последней заявки, а не коэффициент к текущим минутам.

### Что делать и чего не делать

Согласен с порядком в первом разборе: сначала наблюдения и привязка координат,
потом калибровка только там, где группа поездок это показывает.

`snap_distances_meters` уже есть в ответе `OsrmTableClient.matrix`, а
`travel_from_gateway` в манифест плана их не кладёт. Их стоит сохранять в
диагностике вместе с идентификаторами точек. Порог, который отклоняет план,
имеет смысл только после просмотра реальных адресов: большая привязка бывает
и ошибкой геокодера, и нормальным двором.

До этих данных не стоит вводить общий множитель «на пробки», запас с
выбранной константой, штраф за каждый поворот поверх профиля и подмену
непостроенного маршрута прямой. Правило `distance_meters == 0 → 0 минут` тоже
не менять вслепую: для разных домов, схлопнутых в один узел графа, нулевая
дистанция может скрывать ненулевое время, но без примеров правка либо
обнулит реальные совпадающие точки, либо начнёт учитывать шум привязки.

[`simulate_route`](../backend/math_core/simulate.py), сборка графа без файлов
скоростей и то, что [`travel_matrix.py`](../backend/travel_matrix.py)
вызывается только из `scripts/build_travel_matrix.py` и тестов. Все проверенные
утверждения документа подтвердились; числовой пример сходится
(`ceil(541 / 60) = 10`). Граница между описанием и предложениями выдержана,
ссылки на код точные.

### Согласие с предыдущими разборами

Порядок «наблюдения → привязка координат → калибровка по данным» из первого
разбора правильный: любой множитель или резерв, назначенный до измерений, —
произвольное число. Подтверждается кодом и тезис второго разбора, что один
статический снимок — главное ограничение точности: матрица одна на весь поиск,
а сравнивают маршруты уже округлённые минуты, а не секунды OSRM.

### Что не отметили предыдущие разборы

1. **Отказ маршрутной инфраструктуры возвращается как HTTP 400.** И Gateway
   (`do_POST` отвечает `BAD_REQUEST` на `RoutingError`), и веб-сервер
   (`ContractError, RoutingError` → 400 в [`web.py`](../backend/web.py))
   сообщают о недоступном OSRM тем же статусом, что и о битом JSON. Клиент и
   мониторинг не могут отличить «исправь запрос» от «повтори позже»; корректные
   коды для таких случаев — 502/503. Правка не меняет числа в плане и не
   зависит от накопления наблюдений.
2. **Профиль в URL захардкожен.** `OsrmTableClient` всегда запрашивает
   `/table/v1/driving/...` и `/route/v1/driving/...`; вид транспорта выбирается
   только базовым URL инстанса
   ([`routing_gateway.py`](../backend/routing_gateway.py)). Это работает,
   потому что `osrm-routed` игнорирует сегмент профиля в пути и отвечает по
   загруженному графу. Но конфигурация, где оба URL указывают на один инстанс,
   молча вернёт автомобильные времена для пешеходов — стоит либо проверять
   конфигурацию при старте, либо зафиксировать это допущение в документе.
3. **Один техник с ненастроенным видом транспорта валит весь план.** Если во
   входе есть `vehicle: pedestrian`, а `OSRM_FOOT_URL` не задан, `_url_for`
   бросает `RoutingError` — и не строится план целиком, а не только маршруты
   этого техника. Fail-fast здесь осознанный и правильный (тихий откат на
   автомобильную матрицу хуже), но связь «vehicle ↔ настроенный OSRM-инстанс»
   в документе стоит назвать явно.
4. **Матрицу можно кэшировать между запросами плана.** Матрица — чистая
   функция от версии графа, набора координат и вида транспорта; манифест уже
   несёт `graph_version`, значит инвалидация кэша определена точно. Кэш с
   ключом «версия графа + набор точек + mode» сохраняет принцип «один снимок
   на расчёт» и воспроизводимость, но убирает обращение к OSRM из критического
   пути дневного перепланирования (`planning_reason=replan`). Это улучшение не
   требует наблюдений и не меняет числа.
5. **Окно ограничивает начало работ, но не их конец.** Проверка
   `service_start > window.end` допускает окончание работ за пределами окна —
   конец ограничен только `shift_end`. Документ описывает это точно («начало
   работ позже конца окна»), но семантику «окно = начать не позже» стоит
   зафиксировать явно: если бизнес ожидает «закончить внутри окна», текущая
   проверка мягче требования.
6. **Завышение от потолка можно оценить заранее.** При равномерном
   распределении дробных частей потолок добавляет в среднем около 0,5 минуты
   на дугу, а `max(1, …)` доводит любую ненулевую суб-минутную дугу до минуты.
   День из восьми переездов получает порядка четырёх лишних минут. Так как
   `travel_minutes` — пятый критерий в `lex_score`, завышение влияет на выбор
   маршрута, а не только на отчётные метрики: варианты с большим числом
   коротких плеч штрафуются сильнее. Это уточняет, а не заменяет тезис второго разбора о
   хранении сырых секунд отдельно от минут поиска.

Мелочи, не требующие отдельного раздела: таймаут обращения бэкенда к Gateway
захардкожен (30 секунд на вид транспорта, без общего бюджета на запрос), а
Gateway принимает в `/internal/routing/v1/matrix` поля `coverage_id`,
`sources`, `destinations`, но читает только `coordinates` и `mode` —
поверхность API обещает частичные матрицы, которых нет.

### Итог

Документ пригоден как спецификация действующего расчёта. К предложенному в
первом разборе порядку добавлю параллельную дорожку правок, не зависящих от наблюдений:
статусы ошибок (п. 1), кэш матрицы (п. 4), явная проверка конфигурации режимов
(п. 2–3) и фиксация семантики окна (п. 5). Калибровки скоростей и резерва —
только после накопления данных, как и предлагалось в первых двух разборах.

## Технический разбор 4

Раздел проверен по коду 24 сентября 2026 года независимо: подмена `travel`
в `POST /api/plan` до `parse_problem`
([`web.py`](../backend/web.py)), формула
`0 если метры равны 0, иначе max(1, ceil(секунды / 60))` в
[`travel_from_gateway`](../backend/routing_gateway.py), `symmetric=false`,
порядок поиска дуги в `TravelTable.get`
([`models.py`](../backend/math_core/models.py)), формулы прибытия, окна и
сдвига `departure_at` в
[`simulate_route`](../backend/math_core/simulate.py), сборка графа без
файлов скоростей и то, что
[`travel_matrix.py`](../backend/travel_matrix.py) в путь `gateway` не
входит. Числовой пример сходится: `ceil(541 / 60) = 10`. Граница между
описанием и предложениями выдержана. С существенными тезисами всех трёх
авторов согласен: один статический снимок на план — главное ограничение
точности; любой множитель или резерв до измерений произволен; правило
`distance_meters == 0 → 0 минут` нельзя менять вслепую.

### Что не отметили предыдущие разборы

1. **Дорога округляется вверх, ожидание — вниз.** В
   [`simulate_route`](../backend/math_core/simulate.py) минуты дороги
   берутся уже потолком из дуги (`max(1, ceil(...))`), а минуты ожидания
   считаются как `int((service_start - arrival).total_seconds() // 60)` —
   это отсечение дробной части, не округление. Если инженер прибыл в 09:10:00,
   а окно открывается в 09:30:30, `wait_minutes` будет 20, хотя реальное
   ожидание — 20 минут 30 секунд. Сами часы внутри симуляции точны:
   `arrival`, `service_start` и `service_end` хранят `datetime` целиком, и
   `moment = service_end` переносит секунды на следующую дугу. Дрейф
   накапливается только в отчётных целочисленных полях `Stop`, а не в
   логике выполнимости. Но `travel_minutes + wait_minutes + duration_minutes`
   не обязано сходиться с разностью `service_end - departure_at` в целых
   минутах — это нужно учитывать при сверке отчёта с фактическим графиком и
   при выборе резерва (если резерв считать в тех же отсечённых минутах, он
   систематически занижен относительно дороги).
2. **Одно и то же число OSRM округляется по-разному в `/api/plan` и
   `/api/route`.** В плане дуга получает `ceil(seconds / 60)` целых минут,
   а в геометрии для карты
   ([`OsrmTableClient.route`](../backend/routing_gateway.py),
   [`web.py`](../backend/web.py)) — `round(seconds / 60, 1)` с одним
   знаком. Для переезда в 541 секунду план покажет 10 минут, а карточка
   маршрута на карте — 9.0 минуты. Расстояние в обоих случаях одинаково
   округлено до трёх знаков, поэтому расхождение только в времени. Это не
   баг, а разные назначения полей, но пользователь, сравнивающий план и
   карту, увидит несовпадение без объяснения. Стоит либо зафиксировать
   допущение в документе, либо свести округление к одному правилу.
3. **`OSRM_MAX_TABLE_SIZE` молча ограничивает число точек.** По умолчанию
   100 ([`client_from_env`](../backend/routing_gateway.py)); при превышении
   `OsrmTableClient.matrix` бросает `RoutingError`, и весь план не
   строится. Документ этого предела не упоминает. Для MVP с десятком
   техников и заявок это не существенно, но при росте входа отказ наступит
   до того, как планировщик увидит данные, и проявится как HTTP 400 без
   указания на размер. Стоит либо назвать предел в документе, либо
   возвращать его в диагностику наравне с предложением третьего разбора выводить
   `snap_distances_meters`.
4. **Двойная валидация матрицы отражает неясную границу доверия.** Gateway
   уже проверяет матрицу внутри `OsrmTableClient.matrix`
   ([`_square_matrix`](../backend/routing_gateway.py)), но
   `travel_from_gateway` вызывает `_square_matrix` повторно по
   `durations_seconds` и `distances_meters` ответа. Если Gateway — наш
   собственный сервис с детерминированным контрактом, повторная проверка
   избыточна; если ему не доверяют, избыточна первая. Это не ошибка, а
   симптом: граница доверия между бэкендом и Gateway нигде не зафиксирована.
   Та же неясность видна в том, что `travel_from_gateway` отбрасывает
   `snap_distances_meters` и `graph_version` из ответа Gateway, оставляя
   только четыре поля манифеста, — то есть доверяет содержимому, но
   перепроверяет размер. Стоит явно решить, считать ли Gateway
   доверенным источником матрицы, и привести код к одному правилу.
5. **`finish_at` — это конец последней заявки, а не конец смены.** Поле
   `Simulation.finish_at` после цикла равно `moment`, который становится
   `service_end` последней заявки
   ([`simulate_route`](../backend/math_core/simulate.py)). Документ прямо
   говорит, что обратный путь не прибавляется, — но имя `finish_at`
   легко прочитать как «момент, когда техник свободен и вернулся на базу».
   Если позже появится требование «техник должен вернуться к `shift_end`»,
   текущее поле не подскажет, успеет ли он. Стоит либо переименовать поле
   в `last_service_end_at`, либо явно описать в документе, что `finish_at`
   не включает возврат.

### С чем не согласен или где уточню

- С тезисом третьего разбора (п. 4), что кэш матрицы «не меняет числа», — согласен
  только при условии, что ключ кэша включает не только `graph_version` +
  координаты + mode, но и набор точек **в стабильном порядке**. Сейчас
  `points_from_payload` сохраняет порядок из `locations`, а
  `modes_from_payload` дополнительно сортирует modes через `sorted(set(...))`.
  Если два запроса передадут одинаковый набор точек в разном порядке, ключи
  разойдутся, и кэш не сработает; если порядок совпадёт, но `locations`
  содержат дублирующие координаты с разными `id`, матрицы формально разные,
  хотя числа одинаковы. Это не критично, но «не меняет числа» верно лишь
  при аккуратном ключе — стоит зафиксировать правило нормализации ключа
  до введения кэша, а не после.
- С порядком «сначала наблюдения» из первых двух разборов согласен для калибровки
  скоростей и резерва. Но правки из пунктов 1–5 выше (округление,
  документирование предела, имя `finish_at`, граница доверия) не требуют
  наблюдений и не меняют числа плана — их можно делать параллельно с
  предложениями третьего разбора как уточнения к документу и контракту, а не
  к модели расчёта.

### Итог

Документ точен как спецификация. К независимым от данных правкам третьего разбора
добавлю дорожку чистоты контракта: зафиксировать асимметрию округления
дороги и ожидания (п. 1), свернуть или задокументировать расхождение
`/api/plan` и `/api/route` (п. 2), назвать предел `OSRM_MAX_TABLE_SIZE`
(п. 3), определить границу доверия к Gateway (п. 4) и уточнить семантику
`finish_at` (п. 5). Калибровки скоростей, резерв и правка правила
`distance == 0` — только после накопления наблюдений, в порядке первого разбора.
