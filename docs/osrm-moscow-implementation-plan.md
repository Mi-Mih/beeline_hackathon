# План реализации дорожного движка OSRM для Москвы

Дата: 21 сентября 2026 года.

Статус: утверждаемый план. Этот документ не описывает альтернативы и не
разрешает начало разработки сам по себе.

Связанный ресерч:
[`routing-engine-service-research-plan.md`](routing-engine-service-research-plan.md).

## 1. Зафиксированное решение

Развернуть на одном Linux-сервере собственный **OSRM с алгоритмом MLD** и
использовать его **Table API** для получения матриц времени и расстояния.
Движок и данные не вызываются через публичные API.

Состав решения:

1. OSRM runtime в Docker-контейнере, доступный только во внутренней сети.
2. Routing Gateway — единственная точка доступа приложения к OSRM.
3. Map Manager API и один build worker для загрузки, сборки и активации карты.
4. SQLite для состояния карты, заданий обновления и расписания.
5. Immutable-каталоги версий карты на локальном диске.
6. Docker Compose для запуска сервисов и systemd timer для расписания.
7. Раздел «Карта региона» в существующем пользовательском интерфейсе.

Выбор окончательный для первой версии: Valhalla, GraphHopper, ORS, CH,
`osrm-datastore`, Kubernetes, Redis и внешняя очередь в эту реализацию не
входят.

OSRM распространяется по BSD-2-Clause: лицензии, подписки и платы за запросы
нет. Данные OpenStreetMap доступны по ODbL и требуют указания авторства.
Платными остаются только собственный сервер, диск, сеть и эксплуатация. Решение
не требует коммерческого traffic-провайдера.

Основание выбора:

- MLD рекомендован OSRM как основной алгоритм;
- Table API возвращает `duration` и `distance` сразу для набора точек;
- известный набор из 84 точек помещается в стандартный лимит OSRM в 100
  координат;
- `osrm-customize` позволяет в будущем менять скорости без повторного
  `extract`, если появится собственный бесплатный источник скоростей;
- стек минимален для одного Linux-сервера и не содержит платных компонентов.

Официальные источники:

- [OSRM и Docker/MLD](https://github.com/Project-OSRM/osrm-backend);
- [OSRM Table API](https://github.com/Project-OSRM/osrm-backend/blob/master/docs/http.md#table-service);
- [инструменты и лимиты OSRM](https://github.com/Project-OSRM/osrm-backend/blob/master/docs/tools.md);
- [лицензия OSRM](https://github.com/Project-OSRM/osrm-backend/blob/master/LICENSE.TXT);
- [выгрузка Центрального федерального округа](https://download.geofabrik.de/russia/central-fed-district.html);
- [лицензия OpenStreetMap](https://osmfoundation.org/wiki/Licence).

## 2. Целевая схема

```text
браузер
  │
  ▼
существующий backend
  ├─ /api/plan ───────────────┐
  ├─ /api/route ──────────────┤
  └─ /api/map/*               │
                              ▼
                      Routing Gateway
                       │            │
                       │            └─ Map Manager + SQLite
                       ▼                       │
                 active OSRM MLD               ▼
                       ▲                  build worker
                       │                       │
                       └── atomic switch ─ candidate OSRM

Диск:
  sources/ → quarantine/ → versions/<version-id>/ → active pointer
```

OSRM не публикуется в интернет и не вызывается браузером напрямую. Это
позволяет gateway ограничивать запросы, проверять координаты, фиксировать
версию графа и сохранять независимость приложения от формата OSRM.

Сборка candidate выполняется параллельно работающему active runtime. Планирование
в это время использует прежнюю карту. После проверок gateway атомарно переводит
новые запросы на candidate; предыдущая версия сохраняется для rollback.

## 3. Структура развёртывания

### 3.1. Сервисы Docker Compose

```text
routing-gateway       внутренний API matrix/route/nearest и переключение версии
map-manager           API состояния, jobs, расписания и истории
map-builder           один worker; osmium + OSRM build tools
osrm-active-car       текущий автомобильный граф
osrm-candidate-car    временный контейнер проверки новой версии
osrm-active-foot      текущий пешеходный граф
osrm-candidate-foot   временный контейнер проверки новой версии
```

Один исходный PBF используется для обоих профилей. `car` и `pedestrian`
нельзя обслуживать одним OSRM-графом: профиль применяется при сборке, поэтому
артефакты и runtime раздельные. Если окончательный production-вход не содержит
пешеходных перемещений, `foot` не запускается; это определяется контрактом
входных данных, а не догадкой по демо-файлу.

Все образы закрепляются точными версиями или digest. Тег `latest` запрещён.
OSRM слушает только внутреннюю compose-сеть. Наружу опубликован только
существующий backend с аутентификацией.

### 3.2. Каталоги на сервере

```text
/srv/beeline-routing/
  config/
    moscow.geojson
    car.lua
    foot.lua
  sources/
  quarantine/
  versions/
    <version-id>/
      source.osm.pbf
      moscow.osm.pbf
      car/
      foot/
      manifest.json
      validation.json
  state/routing.sqlite3
  logs/
  active -> versions/<version-id>
  previous -> versions/<version-id>
```

Каталоги версий не изменяются после сборки. `active` и `previous` — атомарно
переключаемые указатели. Хранятся active, previous и один последний failed
candidate для диагностики; остальные версии удаляет безопасный cleanup.

### 3.3. Ограничения ресурсов

- runtime имеет зарезервированные CPU и RAM;
- builder получает более низкие CPU/I/O priority и жёсткий лимит RAM;
- до скачивания проверяется место для исходного PBF, двух наборов артефактов и
  временных файлов;
- одновременно разрешён только один update job;
- matrix-запросы имеют ограничение concurrency и короткую отдельную очередь;
- конкретные значения CPU, RAM, disk и concurrency фиксируются после замера на
  целевом сервере и московском PBF.

## 4. Первая инициализация карты Москвы

### 4.1. Подготовка покрытия

До запуска администратор утверждает `moscow.geojson`: административную границу
Москвы и необходимый дорожный буфер. Буфер обязателен, если бригады могут
стартовать, завершать маршрут или объезжать заторы за административной
границей. Его размер нельзя выбирать без фактической географии заявок.

В репозитории конфигурации сохраняются:

- полигон и его SHA-256;
- источник границы и дата получения;
- контрольные точки внутри Москвы, в Новой Москве и у границы;
- допустимая максимальная дистанция привязки точки к дороге.

### 4.2. Получение исходных данных

Managed source для первой версии:

```text
https://download.geofabrik.de/russia/central-fed-district-latest.osm.pbf
```

Это бесплатная регулярно обновляемая выгрузка OpenStreetMap. Она шире Москвы,
поэтому не передаётся OSRM целиком. Worker:

1. скачивает PBF потоково во временный файл;
2. ограничивает размер и время операции;
3. вычисляет SHA-256;
4. проверяет PBF через `osmium fileinfo`;
5. извлекает timestamp данных из заголовка PBF;
6. выполняет `osmium extract` по `moscow.geojson` с сохранением полных ways;
7. повторно проверяет полученный `moscow.osm.pbf`.

Freshness в UI считается по timestamp данных внутри PBF, а не по времени
скачивания.

### 4.3. Сборка графов

Для автомобиля:

```text
osrm-extract -p /profiles/car.lua /build/moscow.osm.pbf
osrm-partition /build/moscow.osrm
osrm-customize /build/moscow.osrm
osrm-routed --algorithm mld --trial /build/moscow.osrm
```

Для пешеходного режима повторяется та же цепочка с `foot.lua` в отдельном
каталоге. Собственные профили начинаются как зафиксированные копии профилей
выбранной версии OSRM. Любое изменение профиля создаёт новую версию графа и
новый `profile_hash`.

`manifest.json` содержит source URL, source timestamp, SHA-256 исходного и
вырезанного PBF, версию OSRM, digest образа, хэши полигона и профилей, время
сборки и размеры артефактов.

### 4.4. Проверки перед первой активацией

Candidate не активируется, пока не пройдены:

1. `/nearest` для всех контрольных и фактических координат;
2. `/route` для контрольных пар по центру, окраинам и Новой Москве;
3. `/table` для полного репрезентативного набора;
4. отсутствие `null` во всех обязательных ячейках матрицы;
5. проверка направленности: `A → B` не заменяется значением `B → A`;
6. сравнение расстояний и времени с текущей матрицей;
7. регрессионный запуск солвера и сравнение назначений, опозданий и суммарного
   времени движения;
8. измерение p50/p95 latency, RAM и размера графа;
9. проверка route geometry для карты в UI;
10. наличие attribution OpenStreetMap в UI.

Пороговые значения качества утверждаются по результатам первого baseline.
До их утверждения автоматическая активация запрещена.

### 4.5. Первая активация

1. Map Manager переводит версию в `ready`.
2. Запускается candidate runtime на отдельном внутреннем порту.
3. Gateway выполняет readiness и canary-запросы.
4. Новая версия становится `active` одним изменением routing target.
5. Версия записывается в SQLite и возвращается во всех ответах gateway.
6. Старый runtime завершает уже начатые запросы и останавливается.
7. Предыдущая версия сохраняется как `previous`.

При любой ошибке активный указатель не меняется.

## 5. Получение времени и расстояния расчётным сервисом

### 5.1. Внутренний контракт

Расчётный сервис обращается не к OSRM, а к gateway:

```http
POST /internal/routing/v1/matrix
Content-Type: application/json

{
  "coverage_id": "moscow",
  "mode": "car",
  "coordinates": [
    {"id": "office-1", "longitude": 37.6176, "latitude": 55.7558},
    {"id": "request-42", "longitude": 37.6428, "latitude": 55.7642}
  ],
  "sources": "all",
  "destinations": "all"
}
```

Gateway вызывает один OSRM Table request:

```text
/table/v1/driving/<lon,lat;...>?annotations=duration,distance
```

Ответ gateway:

```json
{
  "graph_version": "moscow-20260921T120000Z-a1b2c3d4",
  "engine": "osrm",
  "algorithm": "mld",
  "profile_version": "car-<sha256>",
  "durations_seconds": [[0, 754.2], [811.8, 0]],
  "distances_meters": [[0, 9821.4], [10104.7, 0]]
}
```

Адаптер plan-input один раз преобразует единицы:

```text
travel_minutes = 0 для диагонали, иначе max(1, ceil(seconds / 60))
distance_km = meters / 1000
```

Матрица остаётся направленной. Если OSRM вернул недостижимую пару, таймаут или
неполный ответ, построение нового плана завершается диагностируемой ошибкой.
Средняя скорость, haversine и публичный OSRM как fallback запрещены.

### 5.2. Изменения текущего приложения

Текущий [`backend/travel_matrix.py`](../backend/travel_matrix.py) выполняет
отдельный Route-запрос на каждую направленную пару. Его нужно заменить
`GatewayTableProvider`, который:

- отправляет один полный Table-запрос для набора до 100 координат;
- для большего набора выполняет прямоугольные блоки `sources × destinations`,
  не теряя направленность;
- проверяет размерность, числа, единицы и отсутствие обязательных `null`;
- пинит `graph_version` на всю сборку plan-input;
- сохраняет версии графа и профиля в build manifest;
- использует bounded retry только для целого идемпотентного запроса.

В [`backend/web.py`](../backend/web.py):

- `/api/plan` сначала запрашивает матрицу gateway и только затем вызывает
  солвер;
- `/api/route` получает geometry через gateway из той же active-версии;
- URL публичного `router.project-osrm.org` удаляется из production-пути;
- ошибка маршрутизации возвращается пользователю отдельно от ошибки солвера.

Кэш ключуется по ordered coordinates, mode, graph version и profile version.
После активации карты старые записи не используются для новой версии.

## 6. Обновление карты после первой инициализации

Ручное скачивание, upload и расписание запускают один и тот же pipeline:

```text
queued → downloading/uploading → validating → clipping → building
       → testing → ready → activating → active
```

Ошибочные конечные состояния: `failed`, `cancelled`, `no_change`.

### 6.1. Ручное обновление из Geofabrik

`POST /api/map/updates` создаёт job и сразу возвращает `202 + job_id`.
Загрузка выполняется в фоне. Повторное нажатие во время активной job возвращает
тот же job, а не запускает вторую сборку.

Если SHA-256 и source timestamp не изменились, job завершается как `no_change`.
Обновление никогда не вызывается из `/api/plan`.

### 6.2. Загрузка пользовательского PBF

`POST /api/map/uploads` принимает только `.osm.pbf` как multipart stream:

- файл пишется в quarantine под серверным именем;
- действуют лимиты размера и времени;
- формат проверяется по содержимому;
- после проверки выполняются тот же clip, build и test;
- browser filename не используется как путь;
- upload не меняет managed source для последующих автообновлений.

### 6.3. Автообновление

Пользователь сохраняет интервал и локальное время. Map Manager записывает
настройку, а systemd timer вызывает ту же команду создания update job. Timer не
содержит отдельной логики сборки.

Если предыдущая job ещё выполняется, новый запуск пропускается с записью в
историю. Ошибка обновления не останавливает active OSRM и не блокирует план.

### 6.4. Rollback

Администратор может активировать `previous`, если она собрана совместимой
версией OSRM и прошла проверки. Rollback использует ту же blue/green-процедуру,
не пересобирает PBF и записывается в audit log.

## 7. API управления картой

```text
GET    /api/map/status
GET    /api/map/versions
GET    /api/map/jobs?limit=20
POST   /api/map/updates
POST   /api/map/uploads
DELETE /api/map/jobs/{job_id}
PUT    /api/map/schedule
POST   /api/map/versions/{version_id}/activate
```

`GET /api/map/status` возвращает:

```json
{
  "coverage": "Москва",
  "state": "ready",
  "active_version": "moscow-20260921T120000Z-a1b2c3d4",
  "source_timestamp": "2026-09-21T00:00:00Z",
  "activated_at": "2026-09-21T12:40:00Z",
  "modes": ["car", "pedestrian"],
  "schedule": {"enabled": true, "interval": "P7D", "local_time": "02:00"},
  "current_job": null
}
```

Update, upload, cancel, schedule и rollback требуют административной роли.
Просмотр статуса доступен оператору планирования. Точные роли должны быть
подтверждены заказчиком до реализации авторизации.

## 8. Изменения пользовательского интерфейса

### 8.1. Точка входа

В header существующего [`frontend/index.html`](../frontend/index.html) добавить
кнопку **«Карта региона»** рядом с «Загрузить JSON». Кнопка открывает modal или
правую панель; отдельный SPA для первой версии не нужен.

Рядом со статусом плана показывается компактный статус карты:

```text
Карта Москвы · актуальна на 21.09.2026
```

Цвет отражает состояние: active, устарела, обновляется, ошибка последнего
обновления. Ошибка update не должна выглядеть как недоступность active runtime.

### 8.2. Состав панели «Карта региона»

Блок «Текущая карта»:

- Москва;
- версия графа;
- дата данных OSM;
- дата активации;
- поддерживаемые режимы;
- состояние OSRM;
- кнопка «Обновить из OpenStreetMap».

Блок «Загрузить файл»:

- выбор `.osm.pbf`;
- ограничение размера до начала upload;
- подтверждение запуска длительной фоновой операции;
- прогресс загрузки отдельно от прогресса сборки.

Блок «Автообновление»:

- переключатель;
- интервал из разрешённого сервером списка;
- локальное время запуска `Europe/Moscow`;
- дата следующего запуска;
- кнопка «Сохранить».

Блок «Текущее обновление»:

- стадия и процент только там, где он реально измерим;
- длительность;
- пояснение, что планирование работает на прежней карте;
- кнопка «Отменить» до стадии activation.

Блок «История»:

- source timestamp, инициатор, способ (`download`, `upload`, `schedule`), итог;
- краткая ошибка и ссылка на диагностические детали;
- действие «Вернуть эту версию» только для совместимой ready/previous версии и
  только администратору.

В footer карты сохранить обязательное `© OpenStreetMap contributors`. Ссылка
на OSRM — полезна, но не заменяет attribution OSM.

### 8.3. Поведение frontend

В [`frontend/app.js`](../frontend/app.js) добавить отдельное состояние
`mapManagement`, не смешивая его с `state.busy` расчёта плана.

- status загружается при старте и при открытии панели;
- при активной job выполняется polling с ограниченным интервалом;
- закрытие панели прекращает polling;
- upload показывает сетевой прогресс, затем переключается на server stages;
- кнопки update/upload блокируются только на время существующей update job;
- кнопка планирования остаётся доступной, пока active runtime healthy;
- после активации очищается `routeGeometryCache`;
- ошибки API выводятся понятным сообщением и `job_id` для поддержки.

## 9. Порядок реализации

### Этап 1. Подготовить инфраструктурный каркас

- зафиксировать OSRM image digest и версии osmium/Docker Compose;
- создать каталоги и права `/srv/beeline-routing`;
- добавить Compose services, health checks и внутреннюю сеть;
- реализовать SQLite migrations и модели Coverage, MapVersion, UpdateJob;
- добавить resource limits, local lock, structured logs и recovery после reboot.

Результат: сервисы запускаются, но production-карта ещё не активирована.

### Этап 2. Реализовать первичную сборку Москвы

- получить и утвердить `moscow.geojson` с необходимым буфером;
- реализовать download, checksum, fileinfo, clip;
- собрать car и требуемые production-профили MLD;
- создать manifest;
- выполнить canary, matrix и solver regression;
- активировать первую версию вручную.

Результат: внутренние matrix и route endpoints работают на Москве.

### Этап 3. Подключить расчётный сервис

- реализовать Routing Gateway и `GatewayTableProvider`;
- перевести сборку travel matrix с pairwise Route на Table;
- пинить graph version и строго проверять полноту;
- перевести `/api/route` на локальный gateway;
- добавить contract, integration и load tests;
- обновить `docs/distance-definition.md` новой production-семантикой.

Результат: план и отображаемые линии используют один локальный граф.

### Этап 4. Реализовать обновления

- background jobs, manual download и upload quarantine;
- candidate runtime, проверки, atomic switch и drain;
- cancel, cleanup, retention и rollback;
- systemd timer и настройку расписания;
- audit log, метрики и alerts.

Результат: карта обновляется без остановки планирования.

### Этап 5. Добавить UI

- кнопка и статус «Карта региона»;
- текущая версия и свежесть;
- download/upload/schedule;
- прогресс, история, ошибки, cancel и rollback;
- роли, доступность с клавиатуры и адаптивная верстка;
- frontend tests для состояний job и ошибок.

Результат: оператор управляет картой без доступа к серверной консоли.

### Этап 6. Приёмка и запуск

- нагрузочный тест на реальном количестве точек и параллельных планах;
- обновление во время планирования под resource limits;
- тесты invalid PBF, network failure, OOM, kill и reboot;
- подтверждение rollback;
- проверка отсутствия публичного OSRM в production traffic;
- проверка OSM attribution и отсутствия лицензионных/API-платежей;
- runbook для оператора и администратора;
- только после этого включение расписания.

## 10. Критерии готовности

Решение принято, если одновременно выполнено следующее:

1. Один Matrix API request возвращает полные направленные duration/distance для
   84 московских точек в пределах утверждённого p95.
2. `/api/plan` не запускает и не ожидает обновление карты.
3. Во время сборки candidate active OSRM продолжает строить планы в пределах
   утверждённого SLA.
4. Некорректный PBF или failed regression не может стать active.
5. Один план целиком использует одну `graph_version`.
6. После reboot восстанавливаются active runtime, расписание и история jobs.
7. Manual download, upload, schedule, cancel и rollback работают из UI согласно
   ролям.
8. UI показывает source timestamp, а не только дату скачивания.
9. Расчёты и route geometry не зависят от публичного OSRM.
10. Нет лицензионной, подписочной или per-request платы за движок и данные;
    отображается attribution OpenStreetMap.

## 11. Данные, которые нужны от заказчика до начала работ

Это не варианты технического решения, а обязательные входные параметры:

1. Подтверждённый максимальный охват заявок и стартовых точек вокруг Москвы —
   для утверждения полигона и дорожного буфера.
2. Фактические production-режимы движения: только автомобиль или также
   пешеходный режим.
3. Роли, которым доступны upload, schedule, cancel и rollback.
4. Характеристики целевого Linux-сервера и доступный диск — для resource limits.
5. Требуемые p95 и число одновременных расчётов; если их пока нет, они
   утверждаются по результатам baseline на целевом сервере.

До получения этих данных можно подготовить каркас и тестовый контур, но нельзя
безопасно принять production-покрытие, ресурсы и права доступа.
