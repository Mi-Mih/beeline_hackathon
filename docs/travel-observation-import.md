# Экспериментальная калибровка времени инженера

Статус: поведение незакоммиченных изменений на 24 сентября 2026 года.
Математика коэффициента описана в
[engineer-travel-time.md](engineer-travel-time.md). Здесь — форма диспетчера,
контракт наблюдений и то, когда коэффициент попадает в план.

## Окно «Калибровка времени»

Кнопка в шапке открывает диалог. В нём две секции.

**Расчёт времени в пути.** Переключатель выбирает режим следующего плана и сам
план не строит:

| Кнопка | `use_travel_history` в следующем `POST /api/plan` | Подпись под переключателем |
|---|---|---|
| Без калибровки | `false` | Время из OSRM без калибровки |
| С калибровкой | `true` | Время из OSRM калибруется по наблюдениям инженера |

Выбор сохраняется в состоянии страницы. Он уходит в расчёт при загрузке JSON,
перепланировании и возврате исходного плана. Ответ плана содержит
`travel_time_calculation.mode`: `osrm` или `engineer_history`.

**Данные поездки.** Поля стоят двумя рядами: инженер, точка А и точка Б, затем
убытие и прибытие. Под ними строка накопленных наблюдений выбранного инженера.
«Сравнить и сохранить» считает фактические секунды как разницу прибытия и
убытия и сопоставляет их с прогнозом.

Прогноз сначала запрашивается у `GET /api/route` (живой OSRM через gateway).
Если gateway недоступен, интерфейс берёт дугу из `travel.legs` уже загруженного
плана: сначала дугу с видом транспорта инженера, затем дугу без `mode`, а при
`travel.symmetric = true` — обратную пару в том же порядке. В результате это
подписано как «Прогноз», а не «OSRM». Если нет ни маршрута, ни дуги, показывается
сообщение, что сервис маршрутов недоступен и в плане нет времени между точками.

Повтор того же наблюдения не создаёт дубликат. Результат показывает прогноз,
факт, разницу и медианный коэффициент инженера. Наблюдения с отношением факта
к прогнозу вне диапазона 0,25–4,0 сохраняются, но не входят в коэффициент.
`calibration_ready` становится истинным при не менее чем 20 сопоставимых
поездках (`CALIBRATION_MIN_OBSERVATIONS`).

Дельта пробега в полосе показателей округляется до 0,1 км, как и само значение
`metrics.distance_km`. После округления нулевая разница не показывается.

## Обязательные поля

| Поле | Значение |
|---|---|
| `technician_id` | стабильный идентификатор инженера |
| `departed_at` | фактический момент выезда в ISO 8601 с часовым поясом |
| `arrived_at` | фактический момент прибытия в ISO 8601 с часовым поясом |

Прибытие должно быть позже выезда не более чем на 24 часа.

## Дополнительные поля

| Поле | Назначение |
|---|---|
| `plan_id`, `request_id` | связь с планом и заявкой |
| `origin_location_id`, `destination_location_id` | точки переезда |
| `vehicle_mode` | `car`, `pedestrian` или другой настроенный режим |
| `osrm_seconds` | исходный прогноз OSRM для будущего сравнения |
| `osrm_distance_meters` | расстояние маршрута OSRM |
| `origin_latitude`, `origin_longitude` | координаты отправления; передаются парой |
| `destination_latitude`, `destination_longitude` | координаты прибытия; передаются парой |
| `graph_version` | версия графа, использованная для прогноза |

Пример файла: [`examples/travel-observations.csv`](../examples/travel-observations.csv).
CSV может использовать запятую или точку с запятой. JSON передаётся массивом
объектов либо объектом вида `{"movements": [...]}`.

## Пакетный API

CSV/JSON остаётся дополнительной возможностью для последующей интеграции с
внешней системой. В основном пользовательском сценарии загружать файл не
нужно.

```text
POST /api/travel-observations/import?filename=movements.csv
Content-Type: text/csv
```

Состояние накопленной выборки доступно через:

```text
GET /api/travel-observations/status
```

По умолчанию данные находятся в `ROUTING_STATE_DB`. Отдельный файл можно
назначить переменной `TRAVEL_HISTORY_DB`.
