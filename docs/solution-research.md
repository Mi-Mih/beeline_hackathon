# Как решать задачу маршрутизации инженеров

Исходный обзор кандидатов (сентябрь 2026). **Принятая production-модель** —
`docs/accepted-model.md`. Результаты проверки гипотез — `docs/experiment-results.md`.
Ниже остаётся исследовательский контекст; пункты «Решение для текущего MVP» и
«путь развития» уже частично перекрыты внедрёнными H002/H005.



## Класс задачи

Это Technician Routing and Scheduling Problem: назначение работ исполнителям и
построение маршрутов с навыками, транспортом, сменами и временными окнами. Для
MVP её удобно рассматривать как VRPTW с дополнительной совместимостью
«заявка — инженер» и возможностью оставить заявку неназначенной.

## Что подтверждают внешние источники

- Официальный пример OR-Tools моделирует VRPTW через матрицу времени, временные
  окна и накопительную Time dimension:
  https://developers.google.com/optimization/routing/vrptw
- Dimensions в OR-Tools предназначены для накапливаемого времени/нагрузки, а
  slack моделирует ожидание:
  https://developers.google.com/optimization/routing/dimensions
- Невыполнимые заявки можно моделировать как пропущенные посещения со штрафом;
  больший штраф заставляет solver в первую очередь увеличивать покрытие:
  https://developers.google.com/optimization/routing/penalties
- PyVRP поддерживает временные окна, длительности обслуживания, разные типы
  транспорта, несколько депо и необязательных клиентов. Это сильный кандидат,
  если задача останется близкой к стандартному VRPTW:
  https://pyvrp.org/
- Исследование динамической multi-skill workforce routing использует сначала
  конструктивную вставку по приоритетам, а затем ALNS; при перепланировании оно
  отдельно изучает «замороженный» ближайший участок плана:
  https://arxiv.org/abs/2309.09321
- Для service technician routing опубликован практический вариант «greedy
  randomized heuristic + simulated annealing», что подтверждает пригодность
  эвристического baseline для быстрого MVP:
  https://doi.org/10.1007/978-3-030-29516-5_86

## Что полезно из материалов прошлых хакатонов

1. `ecup-track2-courier-planning-summary.md`: сильное начальное решение важнее
   дорогой фазы улучшения; полезны regret/cheapest insertion, планирование
   дефицитных исполнителей первым и локальная полировка маршрута позже.
2. `data-fusion-2026-heroes-summary.md`: валидатор правил и маленький ручной
   пример нужны раньше сложного solver; отдельный визуализатор помогает находить
   пересечения маршрутов, простои и пропущенные точки.
3. `bia-cvrptw-2025-summary.md`: полная совместная модель быстро усложняется при
   синхронизации ресурсов; последовательная декомпозиция — нормальный практичный
   первый уровень.

## Решение для текущего MVP

Выбран детерминированный cheapest feasible insertion:

1. Срочные и наиболее ограниченные заявки идут первыми.
2. Неподходящие по навыкам и транспорту инженеры отсекаются.
3. Заявка пробуется во всех позициях маршрутов.
4. Маршрут полностью пересимулируется: поездка, ожидание, начало работы в окне,
   окончание работы до конца смены.
5. Лексикографически предпочитается уже работающий инженер, затем минимальный
   добавочный пробег.

Это не гарантирует оптимум, но даёт быстрое, воспроизводимое и объяснимое решение
для 50–100 заявок.

## Контракт и дальнейшая замена solver

JSON Schema версии 1.0 — публичная граница. UI не должен импортировать классы
`GreedyPlanner` и не должен самостоятельно вычислять расписание. Следующий solver
реализует `Planner.plan()` и возвращает тот же `plan-output`.

Рациональный путь развития:

1. Добавить адаптер и геокодирование исходных CSV.
2. Сравнивать baseline с историческим контрольным распределением по покрытию,
   числу бригад и пробегу, но не считать контроль оптимумом.
3. Реализовать OR-Tools Time dimension, совместимость и penalties за пропуск.
4. Добавить frozen prefix при оперативном перепланировании.
5. Только после измерений добавлять 2-opt, regret-k или ALNS.
