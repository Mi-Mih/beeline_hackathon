# Определение расстояния и времени поездки

Статус: production-модель реализована через OSRM Table в
`backend/routing_gateway.py`; прежняя contextual-модель сохранена как
эксперимент в `backend/travel_matrix.py`.

Этот документ фиксирует, что именно система называет расстоянием между двумя
объектами. Формула `по прямой × коэффициент` и единая средняя скорость не
используются.

## Production-определение

При `ROUTING_MATRIX_MODE=gateway` расстояние от A до B — длина направленного
маршрута, выбранного активным OSRM MLD-графом для конкретного транспортного
профиля. Время — стоимость того же маршрута по весам этого графа.

Gateway одним Table-запросом получает две независимые направленные матрицы:

```text
distance_km(A, B, mode) = distances[A][B] / 1000
minutes(A, B, mode)     = max(1, ceil(durations[A][B] / 60))
```

Для диагонали обе величины равны нулю. Значения `A → B` и `B → A` не
усредняются. Расстояние по прямой, средняя скорость и подмена отсутствующей
дуги другим режимом запрещены. Любой обязательный `null` останавливает расчёт.

Весь plan-input строится на одной `graph_version`. При смене карты кэш старой
версии не используется. Базовый OSM-граф статичен и сам по себе не учитывает
live-пробки; такие данные могут появиться только как отдельная версия весов.

## Экспериментальная contextual-модель

Раздел ниже описывает ранее реализованный эксперимент с несколькими Route
alternatives. Он не используется production-путём OSRM Table и не должен
смешиваться с ним в одном плане.

### Короткое определение эксперимента

**Расстояние от объекта A до объекта B для транспорта M в момент T** — длина
выбранного допустимого маршрута по дорожному графу. Маршрут выбирается среди
нескольких дорожных альтернатив по ожидаемому времени, устойчивости времени в
пути и избыточному пробегу.

Поэтому расстояние:

- считается по дорогам, а не между координатами по прямой;
- относится к конкретному виду транспорта;
- направлено: `D(A, B)` не обязано равняться `D(B, A)`;
- может зависеть от момента поездки, поскольку в разное время оптимальной может
  оказаться другая дорожная альтернатива;
- равно длине выбранного маршрута, а не среднему расстоянию альтернатив.

## Входные данные

Адаптер получает:

1. уникальный идентификатор и проверенные координаты каждого объекта;
2. виды транспорта инженеров;
3. дату и время, для которых строится снимок;
4. до трёх альтернативных маршрутов дорожного движка для каждой направленной
   пары и вида транспорта.

Геокодирование выполняется до построения матрицы. Текущая реализация намеренно
не угадывает координаты по адресу: отсутствие `latitude` или `longitude`
останавливает сборку.

Для автомобильного и пешеходного транспорта должны использоваться разные
графы/профили роутера. Пешеходный маршрут по автомобильному графу с уменьшенной
скоростью не считается допустимым.

## Формальная модель

Пусть кандидатный маршрут `r` состоит из сегментов `e`. Для сегмента известны:

- `Lₑ` — длина в километрах;
- `Cₑ` — класс дороги;
- `Zₑ` — зона движения.

Длина кандидата:

```text
D(r) = Σ Lₑ
```

Контекстное время сегмента:

```text
tₑ = 60 × Lₑ / V(M, Cₑ) × K(T, Cₑ) × Kzone(Zₑ)
```

где:

- `V(M, Cₑ)` — калиброванная скорость транспорта для класса дороги;
- `K(T, Cₑ)` — коэффициент конкретного временного пояса;
- `Kzone(Zₑ)` — локальная поправка зоны.

Ожидаемое время всего маршрута:

```text
E(r) = Σ tₑ + Nturn × Pturn + Nlight × Plight
```

Неопределённость считается по сегментам, а не одним процентом на весь путь:

```text
U(r) = sqrt(Σ (tₑ × Q(Cₑ))²)
```

`Q(Cₑ)` задаёт наблюдаемую изменчивость класса дороги. Итоговая функция выбора:

```text
Score(r) = E(r) + λ × U(r) + μ × D(r)
r*       = argmin Score(r)
```

В матрицу записывается:

```text
distance_km = D(r*)
minutes     = ceil(E(r*))
```

Таким образом, более длинный, но предсказуемый маршрут может победить короткий
нестабильный маршрут. При этом `distance_km` остаётся физической длиной реально
выбранного пути.

## Временной контекст MVP

Реализованы четыре пояса:

| Пояс | Время |
|---|---|
| `morning_peak` | 07:00–09:59 |
| `day` | 10:00–16:59 |
| `evening_peak` | 17:00–19:59 |
| `off_peak` | остальное время |

Это не единая средняя скорость. Каждый класс дороги получает собственную
поправку в каждом поясе. Пешеходный профиль не получает автомобильные поправки
часа пик.

Стартовые коэффициенты находятся в `CAR_PROFILE` и `PEDESTRIAN_PROFILE`. Они
нужны, чтобы механизм работал до появления истории, но не считаются
окончательной калибровкой. После накопления GPS-фактов значения должны
оцениваться по завершённым поездкам отдельно для класса дороги, зоны и пояса.

## Построение матрицы

Для `N` объектов и `M` видов транспорта строятся все
`M × N × (N − 1)` направленных дуг. Дуга объекта в самого себя не хранится:
солвер уже возвращает для неё нулевое время и расстояние.

Результат соответствует `plan-input 1.0`:

```json
{
  "travel": {
    "symmetric": false,
    "legs": [
      {
        "from": "office",
        "to": "request-42",
        "mode": "car",
        "minutes": 31,
        "distance_km": 18.724
      }
    ]
  }
}
```

Для каждой дуги адаптер хранит во внешнем manifest:

- рассмотренные альтернативы;
- ожидаемое время и неопределённость каждой альтернативы;
- итоговый score;
- идентификатор выбранного маршрута;
- время и пояс расчёта;
- SHA-256 готовой матрицы.

Manifest не помещается внутрь `travel`: контракт `1.0` запрещает дополнительные
поля.

## Отказы и деградация

Если дорожный движок не вернул маршрут хотя бы для одной обязательной пары,
сборка всей матрицы завершается ошибкой. Молчаливых замен на гаверсинус,
обратную дугу или автомобильный маршрут другого транспорта нет.

Геометрическая оценка может быть добавлена только как отдельный, явно
разрешённый заказчиком режим деградации с соответствующей меткой в плане. В
текущую реализацию такой режим не входит.

## Запуск

Нужен собственный OSRM или совместимый экземпляр с профилями транспорта.
Входной `plan-input` уже должен содержать координаты.

```bash
python -m scripts.build_travel_matrix \
  input.json output.json \
  --osrm-url http://127.0.0.1:5000 \
  --mode-profile car=driving \
  --departure-at 2026-09-21T08:00:00+03:00
```

По умолчанию рядом с `output.json` создаётся
`output.travel-manifest.json`. После сборки `output.json` передаётся обычному
солверу без специальных режимов.

## Граница текущей реализации

`plan-input 1.0` хранит одно время на направленную пару, поэтому один снимок
строится для одного контекстного момента. Для маршрутов, пересекающих несколько
временных поясов, следующий шаг — итерационный расчёт:

1. собрать матрицу для начала смены и построить план;
2. взять ожидаемые моменты выезда из первого плана;
3. пересчитать используемые дуги в их фактических поясах;
4. повторить планирование до стабилизации, но не более заданного числа итераций.

Это расширение не меняет определение расстояния: меняется только контекст, в
котором выбирается дорожный маршрут.
