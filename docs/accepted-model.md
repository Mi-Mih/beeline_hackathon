# Принятая математическая модель

Документ фиксирует модель, которая сейчас стоит в `backend/math_core/`.
Результаты проверенных гипотез и обоснование выбранного подхода приведены в
`docs/experiment-results.md`.

## Класс задачи

Technician Routing and Scheduling: открытый VRPTW с совместимостью
«заявка — инженер» и правом оставить заявку неназначенной.

Один запуск планирует одну зону на один рабочий день. «Бригада» равна одному
инженеру. Каждую заявку посещают отдельно. После последней остановки возврат в
офис не требуется.

Два режима запуска:

| Причина | Поле `planning_reason` | Солвер |
|---|---|---|
| Штатный расчёт перед сменой | `overnight` | OR-Tools Routing (open VRPTW) |
| Перепланирование в течение дня | `replan` | OR-Tools Routing (open VRPTW) |

Оба режима читают один `plan-input 1.0` и пишут один `plan-output 1.0`. Выбор
солвера — `backend.math_core.select.planner_for`.

## Сущности

- **Заявка** `i`: точка, длительность работ `d_i`, окно начала `[a_i, b_i]`,
  приоритет `urgent | high | normal`, набор навыков, опционально транспорт и
  оборудование, опционально `locked_technician_id`.
- **Инженер** `k`: старт `start_location_id`, готовность `available_from`, конец
  смены `shift_end`, навыки, вид транспорта, набор оборудования.
- **Дуга** `(from, to, mode)`: целые минуты и километры. Режим зависит от
  транспорта инженера; при отсутствии mode-specific дуги берётся общая.

Авария в модели: `duration_minutes = 80` (работы на месте) плюс фактическая
дорога из матрицы. Типовые 20 минут из норматива в длительность заявки не
входят, иначе дорога учитывалась бы дважды.

## Допустимость маршрута

Маршрут инженера `k` — последовательность заявок. Симуляция одна и та же для
всех солверов (`backend.math_core.simulate`):

1. Начало: место `start_location_id`, время `available_from`.
2. На каждую заявку есть дуга нужного режима.
3. Прибытие = окончание предыдущей работы + время дуги.
4. Начало работ = `max(прибытие, a_i)`. Раньше окна ждать можно.
5. Начало работ ≤ `b_i`. Окончание работ может выйти за окно, но не за
   `shift_end`.
6. Заявка совместима с инженером: навыки ⊆, оборудование ⊆, транспорт совпадает
   либо не задан, lock пуст либо равен этому инженеру.
7. Каждая заявка встречается не более одного раза.

Несовместимая или невставляемая заявка остаётся в `unassigned` со стабильным
кодом (`NO_SKILLED_TECHNICIAN`, `NO_REQUIRED_VEHICLE`, `NO_REQUIRED_EQUIPMENT`,
`LOCKED_TECHNICIAN_UNAVAILABLE`, `TRAVEL_DATA_MISSING`, `NO_FEASIBLE_TIME_SLOT`).

Оборудование в production — множество «есть / нет», не количественный дневной
запас.

## Целевая функция

Планы сравниваются лексикографически, меньше — лучше:

```text
(
  unassigned_urgent,
  unassigned_high,
  unassigned_normal,
  used_technicians,
  travel_minutes,
  distance_meters
)
```

Это формализация правила «аварии → подключения → остальные», затем минимум
бригад, затем короче путь. Контрольное распределение из CSV эталоном не
считается.

## Основной расчёт: OR-Tools Routing

Оба триггера, `overnight` и `replan`, выбирают `RoutingPlanner` с лимитом
5 секунд. Причина расчёта остаётся частью контракта и нужна вызывающему сервису,
но больше не переключает математический солвер. Если OR-Tools недоступен или
возвращает недопустимое назначение, используется описанный ниже fallback.

## Fallback: greedy + local search

Конструкция (`GreedyPlanner`):

1. Заявки идут в порядке приоритета, затем по числу совместимых инженеров, затем
   по окну.
2. Для каждой заявки перебираются все допустимые инженеры и все позиции вставки.
3. Маршрут целиком пересимулируется.
4. Для `urgent` и `high` предпочитается более раннее начало работ; затем уже
   открытый маршрут; затем добавочный пробег и время в пути.

Полировка (`LocalSearchPlanner` 1.2, бюджет основного LS 1 с,
best-improvement):

- операторы `reinsert`, `relocate`, `swap`, `2-opt`;
- ход принимается только если лексикографический вектор строго лучше;
- при оценке соседа повторно симулируются только затронутые маршруты, симуляции
  неизменённых маршрутов берутся из кэша (H012);
- после схождения основных операторов в остатке бюджета запускается атомарный
  `route elimination`: заявки короткого маршрута пробуются на остальных
  инженерах, а результат принимается только при строгом улучшении lex (H011);
- после route elimination запускается условное точное переназначение готовых
  последовательностей заявок инженерам (H034): eligibility gate ищет
  взаимозаменяемый цикл, assignment решается встроенным Hungarian algorithm,
  кандидат полностью пересимулируется и принимается только при строгом
  улучшении lex;
- итоговый план заново рендерится общим `simulate_route`, поэтому кэш не
  является источником данных для `plan-output`;
- общий симулятор и тот же lex-score.

Это не доказанный оптимум. На синтетических задачах SCIP (H004) greedy
систематически оставлял зазор по числу инженеров и пробегу; локальный поиск
закрывает большую часть этого зазора за интерактивное время. После внедрения
H012+H011 повторный прогон на 56 fixtures дал 18 улучшений, 38 ничьих и
0 ухудшений против версии 1.0; пять улучшений дополнительно уменьшили число
использованных инженеров. Медианный runtime снизился с 0.243 до 0.132 с,
p95 остался на границе секундного дедлайна.

H034 дополнительно улучшила 13 из 148 fixtures без единого ухудшения и убрала
599 минут поездок суммарно; медианный выигрыш среди сработавших случаев —
42 минуты. Победы пока ограничены специализированными `multiurgent-*` и
`swaptech-*`, поэтому для оценки эффекта на эксплуатации нужен реальный
holdout.

## Модель OR-Tools Routing

Модель (`RoutingPlanner`, лимит 5 с, GLS, Parallel Cheapest Insertion):

- отдельный start и фиктивный zero-cost end на каждого инженера (открытый
  маршрут);
- Time dimension: работа + дорога, slack = ожидание до окна;
- несовместимые пары режутся огромным transit, а не `SetAllowedVehiclesForIndex`;
- `AddDisjunction` со штрафами, которые доминируют по приоритету;
- fixed cost использования инженера;
- целые минуты и метры;
- greedy как запасной incumbent внутри экспериментальной логики; если OR-Tools
  нет или назначение недопустимо по симулятору — откат на local search с
  предупреждением в `diagnostics`.

Вход перепланирования — тот же снимок: оставшиеся заявки, обновлённые
`start_location_id` и `available_from`. Отдельного solver-контракта нет.

Правила событийного перепланирования поддерживаются через необязательный
`replan_context` в `plan-input 1.0`. Он
содержит время события, ID новых заявок, прежние последовательности ещё не
начатых работ и активные работы. Входной снимок исключает завершённые и
активные заявки; для занятого инженера `start_location_id` указывает место
активной работы, а `available_from` — момент не раньше её окончания. Контракт
проверяет эту согласованность. Если новая заявка обычная, `stable-event-insertion`
вставляет её без смены инженеров и порядка прежних заявок. Если поступила
авария, OR-Tools перестраивает оставшиеся заявки с доступностью после уже
начатой работы. Ориентир реакции 1–2 часа выдаёт диагностическое предупреждение
при превышении, но не является жёстким ограничением. Без `replan_context`
сохраняется прежний расчёт по снимку.

## Что сознательно не входит в production

- CP-SAT как основной солвер (H003: incumbent часто лучше greedy, но p95
  превышает 15 с).
- MILP/SCIP как дневной солвер (H004: точный oracle малых задач, не интерактив).
- Frozen prefix при аварии (H006 опровергнута: реакция есть, обещанный префикс
  не удерживается, churn высокий).
- Количественный запас оборудования (H007: без обоснованных запасов из данных
  заказчика вердикт неполный).
- Эвристический pruning дуг в exact-моделях (H008: дуг меньше, incumbent не
  быстрее).
- Взвешенная сумма вместо лексикографического вектора.
- Regret-k, SA/LAHC, LNS, tabu, мультистарт, ejection chains, cluster-first,
  beam elimination, adaptive operator ordering, pairwise merge, segment
  evaluation, phase shares, limited-discrepancy и matching-lookahead как
  включённые по умолчанию фазы: в H010–H047 они дали регрессии,
  невоспроизводимость либо недостаточный устойчивый эффект.
- Route-pool recombination H046: 17/83/0 и 16 настоящих recombined wins, но
  заранее установленный лимит master p95 ≤200 мс превышен (200.011 мс),
  поэтому до отдельного confirmatory-прогона не включена.
